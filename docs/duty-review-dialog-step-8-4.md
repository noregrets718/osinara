# Шаг 8.4. Сверка спорной записи через диалог владельца

## Задача и результат

При сетевом сбое Google мог изменить ячейки, а агент не получить ответ.
Повторять такую запись нельзя: предыдущий шаг сохраняет `unknown` и блокирует
новые записи в эту таблицу. Теперь владелец сможет посмотреть фактическое
состояние и отдельно подтвердить решение о закрытии спорной попытки.

Используется механизм сверки из шага 7.3. Добавлены два инструмента:

- `inspect_duty_sheet_write`: список незавершённых операций и просмотр сверки;
- `resolve_duty_sheet_write`: закрытие конкретной попытки по сохранённому
  снимку и личному подтверждению владельца.

Код находится в форке. Работающая установка и реальные Google-таблицы
не обновлялись. Утверждение и публикация графиков появятся следующими шагами.

## Пример диалога

Владелец: «Разберись с зависшим изменением фамилии».

Агент получает список операций своей семьи, уточняет нужную при нескольких
вариантах и вызывает просмотр. В личном чате он показывает:

```text
Состояние при просмотре: unknown.
Текущие данные совпадают с ожидаемыми, но это не доказывает успешность
именно прежнего запроса: данные мог изменить человек.
'Жильцы'!C2: было "Пробный"; планировалось "Учебная"; сейчас "Учебная".
```

Просмотр ничего не отправляет и не снимает блокировку. Если владелец решает
закрыть попытку, агент передаёт `confirmationInput` в отдельный инструмент.
Окно Telegram показывает сохранённые факты, исходную таблицу, старый и выбранный
для сверки Google-профили, смысл решения и последствия. Для неопределённого
исхода кнопка называется «Принять состояние и закрыть попытку».

После согласия состояние проверяется повторным чтением. При совпадении
с просмотром сохраняется решение и статус `reviewed`, а не `applied`.
Возвращается `resolved: true`, но `completed: false`: попытка закрыта,
успешность старой отправки этим не доказана.

| `agent/lib/duty-scheduling/duty-review-previews.ts` | Неизменяемые снимки для окна подтверждения |

| `agent/lib/duty-scheduling/duty-review-approval.ts` | Проверенные факты и подпись кнопки Telegram |
| `agent/lib/duty-scheduling/duty-sheet-write-log.ts` | Список незавершённых операций своей семьи |
| `scripts/demo-duty-review-dialog.ts` | Учебный сценарий сбоя, сверки и повтора без отправки |

```text
unknown → список операций → просмотр под блокировкой исполнителя
                         → чтение таблицы → сохранённый снимок
                         → отдельное личное подтверждение
                         → повторная проверка исполнителя и таблицы
                         → решение владельца → reviewed
```

Это несколько небольших модулей с разными обязанностями: диалог организует
действия, хранилище сохраняет снимки, представление формирует текст, а механизм
шага 7.3 защищает состояние операции. Функции отправки Google в диалоге
и механизме сверки отсутствуют.

## Входные данные

Незавершённые операции:

```json
{ "action": "list" }
```

Результат содержит до 50 операций: ID, исходную таблицу, профиль, состояние,
код ошибки и время создания. При наличии следующей страницы возвращается
`nextOffset`; его нужно передать в новом `list`. Список ограничен своей семьёй,
а в нём остаются только `checking`, `writing` и `unknown`.

Просмотр выбранной попытки:

```json
{ "action": "inspect", "operationId": "<UUID из списка или результата записи>" }
```

Если прежний личный Google-профиль больше не действует, владелец может выбрать
новый доступный профиль. Тогда передаётся его `profileRef` из результата
существующего Google-инструмента. Таблица остаётся исходной; автоматически
подменять профиль или брать текущую таблицу группы нельзя. Выбранный профиль
входит в снимок и подтверждение.

Для решения передаётся только объект из `confirmationInput`:

```json
{ "previewId": "<UUID сохранённой сверки>" }
```

Поля решения, хеш, ячейки и источник модель не передаёт. Их сервер извлекает
из неизменяемого снимка. Дополнительные поля отвергаются. Одобрение другого
снимка, другой операции, другого вызова или инструмента не подходит.

## Что означает результат просмотра

| Классификация | Что известно |
| --- | --- |
| `not_sent` | Журнал остался в `checking`: отправка не начиналась. Google не читается |
| `matches_expected` | Проверенные данные дежурств сейчас совпадают с запланированным результатом |
| `differs_from_expected` | Проверенные данные дежурств сейчас отличаются от ожидаемых |

Для начатой записи показываются значения только затронутых ячеек: прежнее,
запланированное и прочитанное сейчас. Классификация сравнивает весь проверенный
набор данных дежурств, поэтому отличаться могут и другие строки.
Дополнительные контакты и полная история не попадают в ответ инструмента.

Совпадение не доказывает происхождение изменений. Даже если ячейка уже имеет
нужное значение, её мог изменить человек. Поэтому автоматического объявления
успеха или снятия блокировки нет.

Для `checking` предлагается закрыть неотправленную попытку. После подтверждения
старый исполнитель не сможет перевести её в `writing`. Для `writing`/`unknown`
владелец принимает наблюдаемое состояние, понимая неопределённость прежнего
исхода. Это объясняется в тексте и названии кнопки, а не заменяется молча
внутренним флагом согласия.

## Зачем сохраняется ещё один снимок

Окно подтверждения должно показать те факты, которые проверил сервер.
Миграция 150 добавляет `duty_sheet_review_previews`. Снимок содержит исходную
операцию, её состояние и контрольную сумму, выбранный профиль, решение и
значения затронутых ячеек. Полные таблицы жильцов и истории в эту новую
запись не копируются. Перед сохранением проверяются контрольная сумма
исходного наблюдения, семья, владелец и неизменность состояния операции.

PostgreSQL запрещает менять или отдельно удалять снимок. Его контрольная
сумма проверяется при загрузке. Исполнение дополнительно сравнивает внутреннее
решение со снимком: подмена профиля, решения или хеша не проходит даже при
наличии подтверждения самого ID.

Перед фиксацией решения таблица читается заново. Изменение данных, профиля
или состояния операции требует нового просмотра и подтверждения. Если Google
недоступен, таблица некорректна или роль владельца отозвана, блокировка остаётся.
Точные записи о подтверждении проверяются до дополнительного чтения Google
и повторно в транзакции сохранения решения.

Наблюдение выполняется для таблицы из журнала исходной попытки. Смена источника
группы или удаление её регистрации не перенаправляют сверку и не уничтожают
архив попытки. Просмотр доступен действующему владельцу своей семьи.

## Активный исполнитель, повторы и ограничения

Сверка использует ту же сессионную блокировку PostgreSQL, что и исполнитель
записи. При занятой блокировке просмотр и решение отклоняются до Google-чтения.
Возраст операции сам по себе не доказывает остановку процесса.

При этом уже принятый Google-запрос может дать поздний эффект после сетевого
сбоя. Сверка не отменяет его и не гарантирует отсутствие будущего изменения.
Владелец видит это ограничение при принятии текущего состояния.

Закрытие переводит конкретную попытку в `reviewed`; другие незавершённые
операции могут продолжать блокировать таблицу. Для новой записи всегда нужны
новый предпросмотр и новое подтверждение. Старый запрос не отправляется снова.

Повтор решения с тем же `previewId` и действующим точным подтверждением
возвращает сохранённое решение без Google-чтения. После неясной ошибки агенту
предписано сначала проверить статус исходной операции инструментом шага 8.3.
Новое решение нельзя использовать как обход повторной отправки старых правок.

Снимок сверки ограничен 128 КиБ. Слишком большой просмотр отклоняется целиком:
ячейки не сокращаются молча. В первой версии отдельный постраничный просмотр
одного большого снимка не реализован. Строгая проверка таблицы из шага 7.1
сохраняется: невалидные данные сначала нужно исправить, а не обходить проверку.

Оба инструмента доступны только основному агенту в обычном личном диалоге
владельца. Групповые, фоновые и дочерние вызовы исключены; обработчик повторно
проверяет контекст, а база — актуальную роль и принадлежность данных семье.

## Учебный запуск и проверки

Нужна отдельная PostgreSQL-база с суффиксом `_test` и миграциями 001–150.
Пример создания контейнера есть в [шаге 7.3](duty-sheets-step-7-3.md#учебный-запуск).
Из корня проекта после миграций:

```sh
DATABASE_URL="$DUTY_DEMO_DATABASE_URL" node --import tsx scripts/demo-duty-review-dialog.ts
```

Скрипт создаёт вымышленные семью и владельца, имитирует применение ячейки
и последующий сетевой сбой, показывает список и сверку, затем имитирует
использованное личное подтверждение только в учебной базе. После решения
переподключается и повторяет вызов. В конце удаляет только свои тестовые записи.

Ожидаемые строки:

```text
После сбоя: unknown
Незавершённых операций: 1
После решения: reviewed; completed=false; resolved=true.
Повтор: reviewed; новых чтений: 0.
Всего отправок модели Google: 1. Сверка ничего не отправляла.
```

Демонстрация и интеграционные тесты прошли под ограниченной ролью `osinara_app`
на отдельном временном PostgreSQL. Реальные Google и Telegram не вызывались.
Прошли 466 тестов в 29 файлах: дежурства, доступность инструментов,
представление/доставка/группировка подтверждений. Новые проверки включают
реальный lease исполнителя, неизменность снимка, другой профиль, изменённую
таблицу, недоступный Google, отозванную роль, чужую семью, страницы списка,
архивную операцию и повтор после переподключения без отправки.

Также прошли проверка типов всего проекта, целевой `oxlint`, сборка основного
агента `eve build --skip-sandbox-prewarm` и проверка собранного каталога
`scripts/validate-eve-tool-surface-build.ts`. Подготовка sandbox и агрегированная
сборка всех приложений не входили в прогон. Реальный личный диалог и Google
потребуют отдельной приёмки перед выпуском.

Следующий шаг 9.1 — личное подтверждение конкретной версии графика. Публикация
этой версии в выбранную группу будет отдельным изменением.
