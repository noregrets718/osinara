# Порядок разработки через форк

## Договорённость о работе

Все изменения приложения делаются через форк
`https://github.com/ilkruglov/osinara` в аккаунте владельца проекта.
Разработка идёт небольшими последовательными изменениями с пояснениями
для junior-разработчика. Функциональные требования находятся в
[согласованном плане](osinara-household-plan.md).

Рабочий форк: [noregrets718/osinara](https://github.com/noregrets718/osinara).
Первое изменение — ветка `docs/household-plan` с требованиями и этим планом.

## Как устроен рабочий процесс

- Исходный репозиторий — `upstream`. Он нужен для чтения исходников и получения
  обновлений автора.
- Форк пользователя — `origin`. В него отправляются наши ветки и коммиты.
- Ветка объединяет изменения одной задачи; например, расчёт доступности.
- Коммит сохраняет небольшой законченный результат вместе с проверками.
- Diff показывает конкретные добавленные, изменённые и удалённые строки.
- Pull request, если используется, показывает изменения ветки для обсуждения.
  Для нашей работы можно создавать его внутри форка. Отправка изменений
  исходному автору — отдельная задача, сейчас она не запрошена.

Первый шаг — подготовить форк и рабочую копию, проверить происхождение веток
и состояние файлов. Базовую ревизию выбираем по актуальному состоянию
исходников и совместимости с установленной версией, фиксируем в отчёте.
Рабочая копия разработки отделена от установленного Docker-приложения.

Каждое изменение должно решать одну задачу. Если шаг получается большим,
он делится на несколько небольших изменений. Рефакторинг постороннего кода
и обновление зависимостей не добавляются в шаг без необходимости.

## Формат объяснения каждого шага

1. **Задача:** какую часть поведения сейчас добавляем и зачем она нужна.
2. **Пример:** небольшой запрос и ожидаемый результат на вымышленных данных.
3. **Код:** какие файлы изменились, за что отвечает каждый и как они связаны.
4. **Разбор:** ключевые функции простыми словами; новые термины объясняются
   при первом использовании. Отдельно объясняются важные проверки и ошибки.
5. **Проверка:** какие команды запущены и что они действительно подтвердили.
   Невыполненные проверки явно отделяются от успешных.
6. **Результат:** ссылка на коммит/изменения в форке и краткое описание того,
   что уже работает и что будет добавлено следующим шагом.

## Последовательность реализации дежурств

| Шаг | Небольшое изменение | Как проверить результат |
| --- | --- | --- |
| 0 | Создать или найти форк, подготовить рабочую копию и ветку, перенести согласованные требования | Проверить URL `origin`/`upstream`, базовый commit и diff документов |
| 1 | Описать формат жильцов, объектов, смен, календаря и правил; добавить вымышленные примеры | Показать конкретные допустимые данные и понятные ошибки некорректного ввода |
| 2 | Рассчитывать утреннюю и вечернюю доступность одного жильца на дату | Проверить всю согласованную матрицу, исключения, неизвестный график и дату выезда |
| 3 | Определять объекты уборки и число мест на дату | Проверить ежедневные объекты, чередование этажей, начальную дату и совместность пары |
| 4 | Рассчитывать нагрузку и порядок кандидатов | Проверить окно D−30 … D−1, учёт утверждённых версий, исключение черновиков и порядок критериев |
| 5 | Совместно распределять исполнителей по всем объектам дня | Проверить пару, максимум одно назначение, нехватку людей и случай, где последовательный выбор мешает полному распределению |
| 6 | Сохранять черновики, утверждённые версии и основания выбора | Проверить неизменность снимков, замену версии и отсутствие двойного учёта нагрузки |
| 7 | Подключить загрузку из Google Sheets и подтверждаемую запись изменений | Проверить сопоставление полей, распознавание ввода, предпросмотр, конфликты строк и ошибки подключения |
| 8 | Добавить инструменты и диалог владельца: подготовка, просмотр, правки, изменение правил | Пройти сценарий запроса графика и изменения правил на тестовых данных |
| 9 | Добавить подтверждение конкретной версии и публикацию в группу | Проверить владельца, адресата, изменённый черновик, повторное нажатие и сбой отправки |
| 10 | Добавить ответы жильцам об опубликованных назначениях | Проверить соответствие действующему графику и разрешённую область данных |
| 11 | Собрать проверенную версию и подготовить обновление установленного приложения | Показать полный сценарий в тестовой группе, результаты проверок и конкретный состав выпуска |

В шагах 1–5 расчёт отделён от Telegram, Google и базы данных: обычные входные
данные преобразуются в результат. Это позволяет проверять правила без
сетевых запросов и реальных жильцов. Подключение сервисов добавляется после
проверки самой логики.

Сохранение данных, Google-интеграция и публикация могут потребовать нескольких
изменений внутри одного шага: сначала модель/хранение, затем инструмент,
затем включение в диалог. Конкретный размер определяется реальным diff.

## После дежурств

Справочник реализуется отдельно, используя тот же постоянный ID жильца:

1. Поля карточки и импорт с проверкой владельцем.
2. Подтверждённая Telegram-привязка.
3. Поиск по имени и уточнение нескольких совпадений.
4. Поиск по автору сообщения, на которое отвечают.
5. Фотография, контакты, архив и согласованные права доступа.

## Начальная подготовка (шаг 0)

Первый шаг содержит два документа в `docs/`: согласованные требования
и порядок разработки, а также два точечных исключения в `.gitignore`,
которые разрешают хранить эти документы в Git. Остальные локальные отчёты
по-прежнему исключены. Код приложения, зависимости и схема базы данных
на этом шаге не меняются.

Форк создан из `ilkruglov/osinara`, базовый commit —
`985db79e550ca84cc95a79d2f172f73cacc2e52c` (исходная версия 1.8.58).
Работающая установка на момент исследования имела версию 1.8.56;
изменения в рабочей копии сами по себе её не обновляют.

В рабочей копии можно проверить:

```sh
git remote -v
git branch --show-current
git diff main...docs/household-plan --stat
```

Первая команда показывает адреса удалённых репозиториев: `origin` — форк,
`upstream` — источник. Вторая показывает текущую ветку. Третья показывает
файлы и размер зафиксированных изменений относительно `main`.

Проверка первого шага: `git diff --check` и проверка относительных ссылок
между документами. Тесты приложения для изменения документации не требуются.
