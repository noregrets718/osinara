# Шаг 8.2. Выбор Google Sheets через личный диалог

## Задача и результат

В шаге 8.1 агент научился готовить черновик из уже сохранённого источника.
Теперь основной агент в личном диалоге владельца может проверить выбранную
таблицу, показать результат и сохранить настройку после отдельного подтверждения.

Добавлены два инструмента:

- `inspect_duty_sheet_source`: прочитать настройку или проверить новую таблицу;
- `configure_duty_sheet_source`: запросить подтверждение и сохранить проверенный выбор.

Работа ведётся в форке. Установленный агент не обновлён; настоящие Google
и Telegram в проверках не вызывались. В первой версии диалога используется
стандартный шаблон листов и столбцов из шага 7.1.

## Пример диалога

Владелец: «Для графиков нашей группы используй эту таблицу: [ссылка]».

Агент получает группы через `manage_duty_schedule groups`, при необходимости
уточняет нужную. Затем проверяет выбранную таблицу через
`inspect_duty_sheet_source preview` и показывает:

```text
Источник для группы «Учебная группа»: [ссылка]
Текущая версия настройки: 0. После подтверждения: 1.
Листов: 9; жильцов: 10; объектов: 6; смен: …; прошлых графиков: …
Часовой пояс: …; версия правил: …; режим истории: …
```

Если владелец выбирает эту настройку, агент передаёт полученный
`confirmationInput` в `configure_duty_sheet_source`. Появляется отдельное
окно Telegram с группой, новой и прежней таблицами, Google-профилями,
номерами версий и последствиями. Кнопка называется «Сохранить источник».
Нажатие разрешает только этот конкретный вызов с этими параметрами.

После подтверждения сервер повторно читает таблицу. Если она или настройка
группы изменились, сохранение отклоняется: нужен новый просмотр и согласие.
При успехе агент может подготовить черновик инструментом шага 8.1.

HITL — подтверждение человеком действия, которое предлагает агент. Здесь
используется уже существующий механизм проекта: собственная система кнопок
и подтверждений для дежурств не добавляется.

```text
preview
  проверить владельца и внешнюю группу
  запомнить текущую версию настройки

  повторное чтение → сравнение контрольной суммы
  сохранение новой версии в транзакции
```

## Разбор входных данных

Просмотр текущего состояния:

```json
{ "action": "get", "groupId": "<UUID группы из groups>" }
```

Если источник ещё не выбран, возвращается `configured: false` и
`configuration: null`. Обращаться к Google для этого не нужно.

Предпросмотр стандартной таблицы:

```json
{
  "action": "preview",
  "groupId": "<UUID группы>",
  "spreadsheetId": "<ID из ссылки владельца>",
  "profileRef": "<личный профиль из результата Google-инструмента>"
}
```

`spreadsheetId` — часть ссылки между `/d/` и следующим `/`, без всей ссылки.
`profileRef` — служебная ссылка на конкретный подключённый Google-профиль.
Агент получает её из результата чтения существующим Google-инструментом
в личной области; придумывать её или брать семейный профиль нельзя.
Авторизация Google и проверка выбранного профиля остаются в прежнем модуле.
Ключи доступа в параметры и результаты этих инструментов не передаются.

`confirmationInput` содержит ID операции, группу, ожидаемую версию,
полную настройку стандартного источника и `readHash`. Агент передаёт объект
целиком, без правок. Изменённая таблица требует нового предпросмотра,
а не ручной подстановки нового хеша.

Нельзя добавить произвольные поля, ID владельца, готовый список жильцов или
историю. `get` с полями предпросмотра также отвергается. Схемы инструментов
имеют корневой объект, который поддерживает Eve; точные сочетания полей
дополнительно проверяются внутри программы.

## Как работает подтверждение

У просмотра политика `not-applicable`: он ничего не сохраняет.
У настройки — `user-approval`: требуется согласие человека.
Но одного описания инструмента недостаточно. При выполнении программа
проверяет сохранённую запись о подтверждении в PostgreSQL.

Запись должна совпадать по личной сессии, Telegram-пользователю, имени
инструмента, ID вызова и контрольной сумме полного входного объекта.
Она должна быть использована, содержать выбор `approve`, не истечь,
а разговор должен оставаться действующим. Подтверждение другого действия,
другого вызова или изменённого хеша не подходит.

Эта проверка выполняется до повторного чтения Google, затем повторяется
при сохранении вместе с проверкой роли. Поэтому прямой вызов обработчика
без прохождения кнопки не позволяет записать настройку.

Текст окна составляет программа из тех же параметров, которые выполнятся,
и действующей группы из базы. Название группы очищается от управляющих
символов. Оно не может добавить в окно собственную строку приложения.
Показываются обе таблицы и оба профиля: замена источника видна владельцу.
Названия стандартных листов перечислены; настройка произвольного сопоставления
столбцов через этот диалог пока запрещена.

## Зачем читать дважды

Контрольная сумма `readHash` вычисляется из источника и полного проверенного
ответа Google. После нажатия кнопки выполняется новое чтение тех же диапазонов.
Изменение даже дополнительного прочитанного столбца изменит сумму. Это
консервативная проверка: лучше повторить просмотр, чем сохранить выбор,
который уже не соответствует просмотренным данным.

Версия настройки проверяется до повторного чтения и внутри транзакции
сохранения. При одновременной замене источника сохранится одна допустимая
версия. Другой запрос получит конфликт вместо тихой перезаписи.

Это не блокировка Google-таблицы. Человек может поменять её после последнего
чтения. Сохраняется настройка источника, а не обещание заморозить таблицу;
при подготовке каждого графика выполняется новое чтение, а его снимок
сохраняется отдельно со своими данными и правилами.

## Повторы, отсутствие истории и права

Каждый предпросмотр получает новый `operationId`. При повторе уже сохранённой
операции с теми же параметрами возвращается её результат с `reused: true`,
без чтения Google. Даже если после неё появилась версия 2, повтор версии 1
не делает её текущей. Актуальное состояние возвращает `inspect get`.
Выполнение повтора всё равно требует действующего точного подтверждения.
После неясного сбоя агенту предписано сначала прочитать состояние, не создавать
новый ID и повторную настройку автоматически.

Таблицу с режимом истории `not_loaded` можно выбрать как источник.
Предпросмотр явно предупреждает, что расчёт пока заблокирован. Автоматического
перехода на нулевую историю нет. Сначала владелец должен явно определить
режим учёта и загрузить необходимые данные.

Оба инструмента доступны только основному агенту в обычном личном диалоге
владельца. Из групповых, фоновых и дочерних запусков они исключены. Обработчик
тоже проверяет контекст; PostgreSQL проверяет реальную текущую роль и группу
своей семьи. Полная таблица, телефоны и фотографии в ответ предпросмотра
не включаются — возвращаются настройка и сводные показатели.

Новая SQL-миграция не требуется. `readHash` сохраняется дополнительным полем
в существующем JSON настройки; старые версии без него остаются читаемыми.
Снимки прежних графиков не переписываются.

## Учебный запуск

Используйте отдельную PostgreSQL-базу с суффиксом `_test`, миграциями 001–148
и, желательно, ограниченной ролью `osinara_app`. Пример создания учебной базы
есть в [шаге 7.3](duty-sheets-step-7-3.md#учебный-запуск).
Из корня проекта:

```sh
DATABASE_URL="$DUTY_DEMO_DATABASE_URL" node --import tsx scripts/demo-duty-source-dialog.ts
```

Скрипт создаёт вымышленные семью и владельца, показывает предпросмотр и текст
окна, имитирует уже использованное подтверждение только в учебной базе,
сохраняет настройку, переподключается и повторяет операцию. Затем подготавливает
черновик через модуль шага 8.1. Проверки SQL и роли настоящие; Google-транспорт
заменён чтением файла `examples/duty-scheduling/sheets-example.json`.

Ожидаемые строки:

```text
Сохранена настройка: версия 1. Проверенных чтений: 2.
Повтор после переподключения: reused=true; чтений по-прежнему 2.
Черновик на 2026-11-09, версия 1.
```

В конце удаляются только созданные скриптом тестовые записи. Реальные Google
и Telegram не вызываются. Утверждение и публикация графика не выполняются.

## Проверки и следующий шаг

Прошли 413 тестов в 25 файлах: модуль дежурств, доступность инструментов,
представление подтверждений, доставка запросов подтверждения и их группировка.
Новые сценарии проверяют изменённые ячейки, смену источника во время чтения,
неверный профиль, некорректный ответ, отсутствие/отказ/истечение подтверждения,
закрытую сессию, отозванную роль, чужую группу и повтор после переподключения.
Интеграционные тесты и демонстрация прошли под ролью `osinara_app` в отдельном
временном PostgreSQL. Проверка типов всего проекта и целевой `oxlint` прошли.

Команда выбранного набора тестов:

```sh
RUN_DATABASE_INTEGRATION_TESTS=true DATABASE_URL="$DUTY_TEST_DATABASE_URL" \
  node_modules/.bin/vitest run agent/lib/duty-scheduling \
  agent/lib/tool-policy/mode-tool-surface.trusted.test.ts \
  agent/lib/tool-policy/mode-tool-surface.test.ts \
  agent/lib/tool-policy/dynamic-capabilities.test.ts agent/lib/tool-surface.test.ts \
  agent/lib/telegram-hitl/approval-presentation.test.ts \
  agent/lib/telegram-hitl/input-request.test.ts \
  agent/lib/telegram-hitl/approval-batch.test.ts --maxWorkers=1
```

Сборка основного агента проверяется командой
`node_modules/.bin/eve build --skip-sandbox-prewarm`, затем запускается
`node --experimental-strip-types scripts/validate-eve-tool-surface-build.ts`.
Подготовка sandbox и полная агрегированная сборка приложений в эту проверку
не входят. Живой диалог с Google и Telegram потребуется при приёмке выпуска.

Следующий шаг 8.3 — правки данных и поддерживаемых правил через личный диалог:
предпросмотр изменений, точное подтверждение и защищённая запись в Sheets.
