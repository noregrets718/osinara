# Шаг 9.1. Личное подтверждение конкретной версии графика

## Задача и результат

Владелец уже может подготовить и посмотреть сохранённый черновик. Теперь
агент сможет запросить отдельное личное подтверждение именно этой версии
и перевести её в `approved`. Назначения утверждённой версии попадут в учёт
нагрузки при новых расчётах.

Добавлен инструмент `approve_duty_schedule`. Он использует существующее
хранилище и проверку подтверждений из шага 6. Публикация в группу — следующий
отдельный шаг. Работающий агент пока не обновлён; новая SQL-миграция не нужна.

## Пример диалога

Владелец: «Утверждаю показанный график на 9 ноября».

Агент берёт `approvalInput` из результата `manage_duty_schedule`
и передаёт его в `approve_duty_schedule`. Появляется окно Telegram:

```text
Действие: утвердить конкретную версию графика дежурств
Группа: Учебная группа (Telegram ID)
Версия правил: …
Полнота: все места закрыты
Замена: в архиве агента на эту дату ещё нет утверждённой версии

Черновик на 2026-11-09, версия 1.
…все назначения, периоды, показатели нагрузки и незакрытые места…
```

Кнопка называется «Утвердить показанную версию». После нажатия сервер
повторно проверяет права, сохранённый расчёт и актуальность версии.
При успехе возвращаются статус `approved` и время утверждения.
Сообщение в общий чат при этом не отправляется.

## Что открыть в VS Code

| --- | --- |
| `agent/lib/tools/approve_duty_schedule.ts` | Описание действия для модели и обязательное подтверждение |
| `agent/lib/duty-scheduling/duty-approval-dialog.ts` | Понятное окно и обработчик личного утверждения |
| `agent/lib/duty-scheduling/duty-owner-view.ts` | Дополнительный объект `approvalInput` из сохранённого черновика |
| `agent/lib/duty-scheduling/duty-schedule-repository.ts` | Общие проверки окна и исполнения, атомарная смена версии |
| `agent/lib/duty-scheduling/duty-snapshot.ts` | Существующий формат ID, контрольной суммы и ожидаемой прежней версии |
| `agent/lib/telegram-hitl/approval-presentation.ts` | Подключение текста и кнопки к Telegram HITL |
| `agent/lib/duty-scheduling/duty-approval-dialog.integration.test.ts` | Проверки настоящих SQL-транзакций и записей о согласии |
| `scripts/demo-duty-schedule-approval.ts` | Учебный сценарий утверждения, повтора и замены |

```text
prepare / get / latest
  → сохранённый график и approvalInput
approve_duty_schedule
  → проверенный снимок → окно с назначениями → личное согласие
  → проверка точного подтверждения
  → блокировка даты группы → проверка последней версии
  → прежняя approved становится superseded
  → выбранная draft становится approved
```

«Атомарно» означает, что замена фиксируется целиком в одной транзакции базы.
Если проверка или запись завершится ошибкой, прежний утверждённый график
останется действующим. Блокировка по группе и дате сериализует конкурирующие
операции: они не смогут одновременно создать две действующие версии.

## Какие параметры передаются

```json
{
  "id": "<UUID сохранённой версии>",
  "contentHash": "<контрольная сумма из результата>",
  "expectedApprovedId": null
}
```

Это объект `approvalInput` из ответа агента, а не набор значений, который
модель должна придумать. `id` выбирает конкретную версию; `contentHash`
связывает её с точными сохранёнными данными, правилами и назначениями.
`expectedApprovedId` указывает прежнюю утверждённую версию в архиве агента
или `null`, если её не было при подготовке черновика.

Вместо `null` при замене передаётся настоящий ID прежней версии, уже записанный
в снимке. Дополнительные поля — группа, новые назначения, исходные данные —
не принимаются. Модель не может заменить состав графика в вызове утверждения.

`approvalInput` возвращается только для черновика, полноту которого разрешают
сохранённые правила. Для утверждённых, заменённых, отменённых и запрещённых
неполных версий он равен `null`. Но даже непустой объект не доказывает,
что черновик до сих пор последний: это повторно проверяет сервер.

## Что проверяет программа

Для окна и исполнения выделены общие функции в хранилище. Они загружают
версию своей семьи, проверяют зарегистрированную внешнюю группу и сохранённый
Telegram ID, затем блокируют день и читают состояние версии.

Проверяются:

1. Контрольная сумма и ожидаемая прежняя версия совпадают со снимком.
2. Утверждается последний черновик на эту дату для этой группы.
3. Действующая утверждённая версия всё ещё та, которую ожидает черновик.
4. Полноту графика разрешают именно сохранённые правила.

При неполном разрешённом графике окно явно сообщает о незакрытых местах
и о том, что правила допускают утверждение. Оно не скрывает нехватку людей.
Если правила запрещают неполноту, окно и исполнение отклоняются.

Заголовок окна показывает действующее название группы и её Telegram ID.
Сам блок расчёта берётся из снимка и может содержать название группы на момент
подготовки. Имена и названия обрабатываются как данные; управляющие символы
не могут добавить собственные строки приложения в окно.

При исполнении дополнительно проверяется использованное личное подтверждение:
оно должно совпасть по владельцу, сессии, ID вызова, имени инструмента и хешу
полного входного объекта. Оно не должно истечь, быть отклонено или принадлежать
закрытому разговору. Текстовое «да» само по себе не заменяет эту запись в базе.

Обработчик допускает только обычный личный диалог основного агента. В каталоге
групповых, фоновых и дочерних запусков инструмента нет. Роль владельца
повторно проверяется в PostgreSQL; её отзыва после показа окна достаточно,
чтобы остановить исполнение.

## Если между просмотром и нажатием что-то поменялось

Новый черновик на ту же дату делает старое подтверждение устаревшим.
Нельзя незаметно утвердить новую версию с прежней кнопкой: у неё другой ID
и другая контрольная сумма. Агент должен прочитать `latest`, показать результат
и получить новое согласие. Отменённый график не возобновляется утверждением.

Смена Telegram ID адресата, удаление регистрации группы или превращение её
в семейную группу также останавливают утверждение.

Изменение Google-таблицы само по себе не пересчитывает сохранённый черновик.
Утверждается показанный снимок с указанной версией правил; Google при этом
не читается. Если нужны новые данные и назначения, сначала нужен новый расчёт
по просьбе владельца. Другие ранее созданные черновики также не пересчитываются
автоматически после утверждения соседней даты.

## Повтор и учёт нагрузки

Повтор того же вызова с тем же действующим подтверждением возвращает прежнюю
утверждённую версию и прежнее время. Запись не создаётся повторно, нагрузка
не удваивается. После ошибки с неясным результатом агенту предписано сначала
прочитать версию через `manage_duty_schedule get`, а не создавать новый график.

При замене окно показывает номера прежней и новой версий. В одной транзакции
прежняя получает `superseded`, новая — `approved`. В истории остаются обе,
но в нагрузке учитываются назначения только действующей версии.
Снимки и доказательства прежнего утверждения не переписываются.

Ответ содержит `approvalPerformed: true`, `approvedAt` и
`publicationPerformed: false`. Утверждение и отправка в общий чат — разные
события. Назвать график опубликованным по одному статусу `approved` нельзя.

## Учебный запуск и проверки

Используйте отдельную PostgreSQL-базу с суффиксом `_test` и миграциями 001–150.
Для этого шага новой миграции нет. Пример создания учебного контейнера есть
в [шаге 7.3](duty-sheets-step-7-3.md#учебный-запуск).
Из корня проекта:

```sh
DATABASE_URL="$DUTY_DEMO_DATABASE_URL" node --import tsx scripts/demo-duty-schedule-approval.ts
```

Скрипт создаёт вымышленные семью и владельца, сохраняет график из примера,
показывает текст окна и имитирует использованное подтверждение только в
учебной базе. Затем утверждает график, переподключается, повторяет вызов
и утверждает изменённую версию. В конце удаляет только свои тестовые записи.

Ожидаемые строки:

```text
Утверждена версия 1; status=approved; publicationPerformed=false.
Повтор после переподключения: та же версия и время — true.
После замены: старая версия superseded; действующих версий: 1; назначений: 6.
Google/Telegram не вызывались; публикации в группу не было.
```

Прошли 491 тест в 31 файле: модуль дежурств, доступность инструментов,
представление/доставка/группировка подтверждений. Миграции, интеграционные
тесты и демонстрация выполнены на отдельном временном PostgreSQL под
ограниченной ролью `osinara_app`.

Новые проверки включают подмену хеша и прежней версии, новый черновик после
показа окна, замену и учёт нагрузки, конкурентные повторы, полноту, отмену,
изменение адресата, чужую семью, отозванную роль и прямые вызовы из запрещённых
контекстов. Прежние проверки хранилища также прошли после выделения общих функций.

Также прошли проверка типов всего проекта, целевой `oxlint`, сборка основного
агента `eve build --skip-sandbox-prewarm` и проверка собранного каталога
`scripts/validate-eve-tool-surface-build.ts`. Подготовка sandbox и полная
агрегированная сборка приложений в прогон не входили. Реальные Google и Telegram
не вызывались; живой диалог потребует приёмки перед выпуском.

Следующий шаг 9.2 — публикация утверждённой версии в выбранную внешнюю группу
с проверкой адресата, версии и защитой от повторной отправки.
