# Шаг 7.3. Постоянный источник и сверка неопределённых записей

## Результат

Внешняя группа получает сохранённую настройку источника Google Sheets.
Она переживает переподключение программы и меняется только новой версией
после точного личного подтверждения владельца.

Для спорной записи теперь есть два отдельных действия: прочитать и показать
текущее состояние; затем, по отдельному подтверждению, закрыть старую попытку
без повторной отправки правок. Результат называется `reviewed`, а не `applied`.

Это внутренние модули. Кнопки и команды Telegram добавляются в шаге 8.
Работающий агент, реальные таблицы и его база не обновлялись.

подтверждение одного действия не разрешает другое.

## Настройка источника по группе

В `dutySheetSourceRepository.save` передаётся:

```ts
{ operationId, groupId, expectedVersion: 0, source }
```

`source` содержит ID таблицы, выбранный Google-профиль и сопоставление листов
и столбцов из шага 7.1. `0` означает, что настройки пока нет.
Первая сохранённая версия получает номер `1`. Для изменения версии `1`
нужно передать `expectedVersion: 1`; новая версия получит номер `2`.

Если две команды одновременно меняют одну версию, сохранится одна.
Вторая получает `AGENT_DUTY_SOURCE_VERSION_STALE`: нужно загрузить текущую
настройку и подтвердить новое изменение. Повтор того же ID с теми же
данными возвращает исходный результат; он не возвращает старую версию в действие.
Текущую настройку всегда возвращает `get`.

Сохранять и читать можно только в контексте личного владельца и для
зарегистрированной внешней группы своей семьи. Все версии неизменяемы.
Удаление регистрации группы сохраняет архив, но запрещает использовать
настройку через эту группу. Новая регистрация не подхватывает её автоматически.

Хранилище проверяет структуру настройки и права, но не выполняет Google-запрос.
Будущий инструмент настройки должен сначала проверить таблицу чтением,
показать её владельцу и затем сохранить подтверждённый выбор.
`readConfiguredDutySheet(groupId, ctx)` уже получает источник из базы,
читает его через существующую Google-интеграцию и повторно проверяет версию
после сетевого запроса. Если источник сменился, прочитанные данные не возвращаются.

## Сверка: наблюдение отдельно от решения

```text
inspect → проверить отсутствие активного исполнителя
        → прочитать таблицу → показать наблюдение и reviewHash

resolve → проверить отдельное подтверждение владельца
        → заново проверить исполнителя и прочитать таблицу
        → сверить reviewHash
        → сохранить решение и перевести попытку в reviewed
```

У `inspect` нет доступа к функции отправки изменений Google.
Он не снимает блокировку и не меняет журнал. Для `writing` и `unknown`
он показывает исходно запланированные ячейки, текущие проверенные данные
и результат сравнения:

| Классификация | Что известно |
| --- | --- |
| `matches_expected` | Сейчас прочитаны данные, совпадающие с ожидаемыми |
| `differs_from_expected` | Текущие данные отличаются от ожидаемых |
| `not_sent` | Запись не была начата: журнал остался в `checking` |

Даже `matches_expected` не доказывает, что именно наш запрос выполнился:
данные мог изменить человек. Автоматического объявления успеха нет.
Для `checking` Google не вызывается, поскольку можно безопасно закрыть
неотправленную попытку без чтения таблицы.

`reviewHash` связывает просмотр с ID и состоянием операции, её исходным
запросом, выбранным профилем и прочитанными данными. Если они поменялись,
старое подтверждение не применяется. После смены Google-аккаунта можно
явно выбрать новый `profileRef` для чтения той же таблицы; он тоже входит
в подтверждаемый снимок.

## Решение владельца

У `resolve` два варианта:

- `cancel_unstarted` — закрыть `checking`. Попытка не отправлялась;
  старый исполнитель больше не сможет перейти к записи.
- `accept_current` — принять наблюдаемое состояние после `writing` или
  `unknown`. Требуется явное `acknowledgeUncertainOutcome: true` и отдельное
  личное подтверждение `resolve_duty_sheet_write`.

Подтверждение должно объяснять владельцу смысл выбора: старые правки
не будут отправлены снова, история неопределённого исхода останется,
а новые записи снова станут разрешены. Значение флага нельзя подставлять
вместо понятного подтверждения в будущем диалоге.

В одной транзакции сохраняются снимок сверки, решение и доказательство
подтверждения, затем состояние меняется на `reviewed`. Прежний план,
подтверждение записи и её код ошибки остаются неизменными. `completed`
остаётся `false`: это решение владельца, а не доказанная успешная отправка.
Новая запись требует нового ID, свежего предпросмотра и подтверждения.
Старый ID больше не отправляется при повторном вызове.

Если доступ к Google пропал или таблица не проходит проверку, сверка
не снимает блокировку. Сначала нужно восстановить доступ или исправить данные.

## Защита от ещё работающего исполнителя

Возраст записи в журнале не доказывает, что процесс остановился. Поэтому
исполнитель держит сессионную блокировку PostgreSQL по ID операции на отдельном
соединении. Сверка пытается получить ту же блокировку и при занятости
возвращает `AGENT_DUTY_SHEET_WORKER_ACTIVE`, без Google-запроса и снятия блокировки.

Отдельное соединение не занимает слот общего пула, пока идёт ожидание Google.
При его потере срабатывает сигнал отмены; перед отправкой и фиксацией успеха
соединение дополнительно проверяется. В тесте соединение действительно
завершалось через PostgreSQL, после чего сигнал операции переходил в отменённое
состояние. Основной контекст другого запроса при этом не отменяется.
Поведение сессионных блокировок описано в
[документации PostgreSQL](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS).
Для этой блокировки требуется соединение с сохраняющейся сессией базы.

Это защита от локального активного исполнителя. Она не доказывает завершение
уже принятого Google-запроса после сетевого сбоя. Поздний ответ или эффект
провайдера остаётся возможным; именно поэтому принятие текущего состояния —
явное решение владельца, а не автоматическое снятие блокировки по таймеру.
Ограничение ручных правок между чтением и записью из шага 7.2 также сохраняется.

## Учебный запуск

Скрипту нужна отдельная PostgreSQL-база с суффиксом `_test` и всеми миграциями.
Google и Telegram заменены вымышленными данными и тестовыми подтверждениями.
Например, на этом сервере используется уже имеющийся образ `d2ef61f42ef7`:

```sh
docker run --detach --name osinara-duty-source-demo \
  --memory 256m --cpus 0.5 --tmpfs /var/lib/postgresql/data:rw \
  --publish 127.0.0.1:55440:5432 \
  --env POSTGRES_DB=osinara_duty_source_test \
  --env POSTGRES_USER=duty_demo \
  --env POSTGRES_PASSWORD=duty-demo-only d2ef61f42ef7
docker exec osinara-duty-source-demo pg_isready -U duty_demo -d osinara_duty_source_test
```

После готовности базы из корня `osinara`:

```sh
DUTY_DEMO_DATABASE_URL='postgresql://duty_demo:duty-demo-only@127.0.0.1:55440/osinara_duty_source_test'
DATABASE_URL="$DUTY_DEMO_DATABASE_URL" node --experimental-strip-types scripts/migrate.ts
DATABASE_URL="$DUTY_DEMO_DATABASE_URL" node --import tsx scripts/demo-duty-sheet-review.ts
```

Результат:

```text
Настройка после переподключения: версия 1
После сбоя: unknown
Наблюдение: matches_expected; журнал остаётся unknown
После отдельного подтверждения: reviewed; completed=false
Всего попыток отправки: 1. Сверка не отправляла правки.
```

В конце скрипт удаляет только свою тестовую семью и пользователей.
После изучения удалить именно учебный контейнер:

```sh
docker rm --force osinara-duty-source-demo
```

пятнадцать сверки и исполнителя). Миграции и интеграционные проверки выполнены
на отдельном временном PostgreSQL под ограниченной ролью `osinara_app`.

затронутых TypeScript-файлов и `git diff --check`.

выбираться сервером из сохранённой настройки группы с привязкой к версии;
низкоуровневый `writeDutySheet` не должен давать модели обходить этот выбор.

и распознавание обычных сообщений/таблиц владельца.
