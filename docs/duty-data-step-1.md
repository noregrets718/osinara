# Шаг 1. Формат входных данных дежурств

## Что добавлено

Программа получает данные извне: позже это будут Google Sheets, распознанная
фотография или сообщения владельца. Перед расчётом нужно убедиться, что
эти данные имеют понятную структуру и не противоречат друг другу.

В этом шаге появилась такая проверка. Она работает локально, без Telegram,
Google и базы данных. Расчёт назначений будет следующим отдельным изменением.

JSON-пример описывает внутренний формат обмена. Он не требует, чтобы владелец
вручную писал JSON в Google Sheets: преобразование столбцов и распознанных
данных в этот формат добавится при подключении источников.

| Файл | Назначение |
| --- | --- |
| `agent/lib/duty-scheduling/duty-data.ts` | Описывает допустимые данные и проверяет их связи |
| `examples/duty-scheduling/example.json` | Вымышленный пример: два жильца 5/2, восемь сменных, шесть объектов |
| `agent/lib/duty-scheduling/duty-data.test.ts` | Проверяет корректный ввод и важные ошибки |
| `scripts/validate-duty-data.ts` | Позволяет проверить пример или свой JSON из терминала |

## Как связаны данные

```text
residents: id = r04, фамилия = Тестов, график = shift
                        ↑
workShifts: residentId = r04, дата = 2026-11-09, состояние = night
```

`id` — постоянный идентификатор записи. `residentId` ссылается на него.
Если изменить фамилию, ссылка на человека сохранится. Одинаковые фамилии
разрешены; одинаковые ID — ошибка. Ввод только фамилии тоже разрешён.

Состояния смен: `day` — дневная смена, `night` — ночная,
`recovery` — отсыпной, `off` — выходной. Отсутствие записи на другую дату
не создаёт смену автоматически.

`activeFrom` — первый день проживания. `inactiveFrom`, если указан, — первый
день после завершения проживания: на него и позднее новые дежурства не назначаются.
На этом шаге проверяется порядок дат; применение границ появится в расчёте доступности.

## Что означают схема и тип

**Схема Zod** описывает допустимые значения во время выполнения программы.
Например, существующую дату `YYYY-MM-DD` или положительное число исполнителей.

**Тип TypeScript** помогает редактору находить ошибки в самом коде.
Тип `DutyData` выводится из схемы через `z.infer`: описание структуры хранится
в одном месте. Сам по себе тип не проверяет содержимое файла из Google или JSON.

`parseDutyData` принимает `unknown`: до проверки содержимому нельзя доверять.
После успешной проверки она возвращает `DutyData`. При ошибке выбрасывает
`AppError` с кодом и путём до проблемного поля.

## Настройки остаются данными

- `schemaVersion` — версия формата данных, сейчас `1`.
- `rules.version` — версия конкретных правил, в примере `initial-1`.
- `rules.availability` — все семь строк согласованной матрицы доступности.
- `rules.weekendDays` — номера дней недели: понедельник `1`, воскресенье `7`.
- `calendarOverrides` — исключения общего календаря; `isDayOff: false`
  означает рабочий день, даже если он попадает на обычный выходной.
- `exceptions` — индивидуальная доступность: можно изменить утро, вечер
  или оба периода. Неуказанный период сохраняет результат основного графика.
- `rules.lookbackDays` — длина окна нагрузки, в примере `30`.
- `rules.maxAssignmentsPerDay` — максимум назначений за день, в примере `1`.
- `rules.priorities` — порядок поддерживаемых критериев выбора.
- `rules.allowIncompleteSchedules` — допускается ли утверждать неполный график.

У объекта уборки `people` задаёт число исполнителей, `samePeriod` — требование
работать в одном периоде, `periods` — допустимые утро/вечер. `creditPerPerson`
задаёт зачёт нагрузки каждому исполнителю. В начальном примере он равен `1`.

`recurrence.everyDays` задаёт периодичность. Для значения больше `1` обязательна
`anchorDate`: дата начала цикла. У второго и третьего этажей даты сдвинуты
на день. Подсчёт дат уборки добавляется в шаге 3.

Часовой пояс `Europe/Moscow` и даты в примере — вымышленные настройки
для разработки; параметры реального дома будут заданы отдельно.

## Как проверить в VS Code

Открой терминал в корне рабочей копии проекта и выполни:

```sh
node --import tsx scripts/validate-duty-data.ts
```

Ожидаемый результат:

```text
Данные дежурств корректны.
Жильцы: 10 (сменных: 8)
Объекты уборки: 6
Записи смен: 8
Версия правил: initial-1
Часовой пояс: Europe/Moscow
```

Можно передать путь к другому JSON:

```sh
node --import tsx scripts/validate-duty-data.ts /путь/к/примеру.json
```

Тесты этого шага:

```sh
npm test -- agent/lib/duty-scheduling/duty-data.test.ts
```

## Какие ошибки обнаруживаются

Несуществующая дата, неизвестный жилец в смене/исключении, повторный ID,
несколько записей одного человека на дату, выезд раньше заселения, смена
у человека 5/2, неизвестный часовой пояс и неполная матрица доступности.
Неизвестные поля и типы правил отклоняются, чтобы опечатка не была молча проигнорирована.

Проверка формата ещё не доказывает, что людей хватит на все объекты.
Это задача будущего распределения; незакрытые места допустимы по согласованным правилам.
История дежурств и запуск счётчика с нуля добавляются в отдельном шаге учёта нагрузки.

## Результат локальной проверки шага

- Тесты контракта проверяют допустимый ввод и отклонение некорректного.
- Команда проверки успешно читает вымышленный пример.
- На смене с неизвестным жильцом команда завершается с кодом `1` и указывает
  поле `workShifts.0.residentId`.
- Проверка TypeScript выполнена для трёх новых файлов кода: контракта, тестов
  и команды проверки. Линтер этих файлов также прошёл.
- Полная проверка типов проекта остановлена по лимиту 60 секунд без результата.
  Это ограничение локальной проверки; успешной полная проверка не объявляется.

Следующий шаг — функция, которая по этим данным определяет доступность одного
жильца утром и вечером на выбранную дату.
