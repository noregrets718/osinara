# Шаг 6. Постоянные черновики и история версий

## Задача и результат

До этого `prepareDutyDraft` возвращала результат в памяти программы.
После завершения команды он исчезал. Теперь модуль сохраняет расчёт в
PostgreSQL: его можно прочитать после переподключения и исправить новой версией.

Пример: на 9 ноября сохранена версия 1 с шестью назначениями. Владелец
подтверждает её, затем сообщает об отсутствии Анны. Программа создаёт
версию 2. После отдельного подтверждения версия 1 получает `superseded`
и остаётся в архиве, версия 2 становится `approved`. Для этой даты
учитываются только шесть назначений версии 2.

Здесь реализован слой хранения. Инструменты агента, показ черновика владельцу,
кнопки Telegram и отправка в группу появятся в шагах 8–9. Утверждение в базе
ещё не означает доставку сообщения в группу. Работающая установка не обновлена;
миграция проверена на отдельном тестовом PostgreSQL 17.10.

## Что значит «снимок»

У каждой версии сохраняются:

- ID, номер версии, дата, семья и точная внешняя Telegram-группа.
- Исходные жильцы, смены, исключения, календарь и правила с их версией.
- История, использованная при расчёте, включая режим начала учёта.
- Готовые назначения, периоды, нагрузка до назначения и причины незакрытых мест.
- ID действующей утверждённой версии, которую этот черновик должен заменить.

Это копия данных на момент расчёта. Чтение старого графика не запускает
распределение заново. Изменения правил применяются к новым расчётам.

`contentHash` — SHA-256 от содержимого снимка с упорядоченными ключами JSON.
Одинаковые данные имеют одинаковую контрольную сумму независимо от того,
как PostgreSQL расположил ключи JSONB. Это проверка целостности и привязка
подтверждения к содержимому, не электронная подпись. ID и версия входят
в снимок: разные версии имеют разные суммы даже при одинаковых назначениях.

Триггер — функция, которую PostgreSQL автоматически вызывает при изменении
строки. Здесь он запрещает перезапись снимка, даты, номера и контрольной суммы.
Изменение назначений требует новой строки. Отдельную архивную версию удалить
нельзя; полное удаление семьи удаляет её архив каскадно. Удаление регистрации
группы сохраняет архив, но запрещает утверждать её ожидающие черновики.

## Сохранение и повтор команды

```text
save(auth, input)
  проверить актуальные права владельца и внешнюю группу
  заблокировать ключ операции и дату до завершения транзакции
  если операция уже сохранена → вернуть прежнюю версию
  собрать действующую историю и рассчитать черновик
  сохранить следующую версию со снимком
```

`operationKey` — уникальный ключ одной пользовательской операции. Повтор
после сетевого сбоя с тем же ключом и данными возвращает прежний ID.
Другие данные с тем же ключом дают `AGENT_DUTY_OPERATION_CONFLICT`.
Для сознательного создания следующего черновика нужен новый ключ.

Транзакция объединяет несколько запросов в одну операцию: либо все
изменения сохраняются, либо все отменяются. Блокировка даты не даёт двум
одновременным запросам присвоить один номер версии. Ключ включает семью,
Telegram-группу и дату: графики разных групп учитываются отдельно.

## Утверждение конкретной версии

Будущий серверный инструмент передаст `approve` три значения:

```ts
{ id, contentHash, expectedApprovedId }
```

Отдельно он передаст реквизиты сохранённого подтверждения Telegram:
`applicationSessionId`, `eveSessionId`, `toolCallId`. Модуль сам проверяет
запись в существующей таблице `telegram_hitl_approvals`:

- Подтверждение относится к инструменту `approve_duty_schedule` и точному вводу.
- Нажатие уже принято, выбран вариант `approve`, срок не истёк.
- Это личный чат текущего владельца той же семьи и действующая личная сессия.
- Подтверждается последний черновик на дату; заменяемая версия всё ещё та же.
- Полнота графика разрешена правилами, сохранёнными в этом снимке.

Проверки владельца повторяются внутри транзакции. `auth` должен строиться
сервером через `requirePrivateTelegramOwner`; его нельзя принимать от модели
как произвольный JSON. Права перепроверяются по базе, поэтому старый контекст
не даёт доступа после отзыва роли.

При успехе прежняя версия становится `superseded`, новая — `approved`.
Оба изменения совершаются в одной транзакции. Ошибка оставляет прежний график
действующим. Индекс базы дополнительно разрешает только одну утверждённую
версию на дату для группы. Точный повтор успешной операции возвращает
прежний результат; устаревшая версия не возвращается в действие.

Имя инструмента пока зарезервировано для будущего подключения. Тесты создают
вымышленные подтверждения непосредственно в отдельной БД; это не рабочий
способ подтверждения для владельца и не обход проверки в Telegram.

## История без двойного учёта

`history` соединяет загруженную историю с утверждёнными версиями этой группы.
На дату, где уже был локально утверждённый график, локальные версии заменяют
все импортированные записи этой даты. Модуль нагрузки из шага 4 учитывает
из них только `approved`.

Черновики ничего не добавляют в нагрузку и не вытесняют импортированные
назначения. Если ранее утверждённая версия отменена, импортированная запись
этой даты не возникает заново. Отменённые и заменённые версии остаются
архивными. Пользовательская команда отмены пока не добавлена.

`not_loaded` остаётся неизвестной историей: наличие отдельных сохранённых
графиков не доказывает полноту прежних данных. Удалённых жильцов и объекты
нужно архивировать в каталоге с прежними ID, чтобы история сохраняла связи.

## Запуск учебного примера на этом сервере

Все команды выполняются из корня рабочей копии в терминале VS Code.
Понадобится отдельный тестовый контейнер. На этом сервере уже есть проверенный
образ `d2ef61f42ef7` с PostgreSQL и pgvector; это локальный ID образа,
а не переносимое имя для другого сервера. Пароль ниже вымышленный, только
для временной базы примера.

```sh
docker run --detach --name osinara-duty-storage-demo \
  --memory 256m --cpus 0.5 --tmpfs /var/lib/postgresql/data:rw \
  --publish 127.0.0.1:55436:5432 \
  --env POSTGRES_DB=osinara_duty_step6_test \
  --env POSTGRES_USER=duty_step6 \
  --env POSTGRES_PASSWORD=duty-step6-test-only d2ef61f42ef7
```

Готовность проверяется командой; после первого запуска может понадобиться
повторить её через несколько секунд:

```sh
docker exec osinara-duty-storage-demo pg_isready -U duty_step6 -d osinara_duty_step6_test
```

Подключение передаётся только конкретным командам:

```sh
DUTY_TEST_DATABASE_URL='postgresql://duty_step6:duty-step6-test-only@127.0.0.1:55436/osinara_duty_step6_test'
DATABASE_URL="$DUTY_TEST_DATABASE_URL" node --experimental-strip-types scripts/migrate.ts
DATABASE_URL="$DUTY_TEST_DATABASE_URL" node --import tsx scripts/demo-duty-storage.ts
```

Миграции создают таблицы отдельной базы. Пример сохраняет и утверждает
вымышленные графики, проверяет переподключение и исправление, затем удаляет
свою тестовую семью и пользователей. Telegram и Google не вызываются.
Скрипт отказывается работать с именем БД без суффикса `_test`.

Основные строки вывода:

```text
Версия 1, статус draft, мест 6/6
Повтор команды вернул тот же ID: true
После переподключения: версия 1, та же сумма: true
После исправления: v1 — superseded, v2 — approved
Действующих версий на дату: 1; назначений в учёте: 6
```

Тесты модуля с подключением базы:

```sh
RUN_DATABASE_INTEGRATION_TESTS=true DATABASE_URL="$DUTY_TEST_DATABASE_URL" \
  npm test -- agent/lib/duty-scheduling --maxWorkers=1
```

После проверки удалить именно учебный контейнер:

```sh
docker rm --force osinara-duty-storage-demo
```

Его данные находятся во временной файловой системе и удаляются вместе с ним.
