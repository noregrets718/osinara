# Дежурства и справочник жильцов в Osinara

Статус: согласованные продуктовые требования и план реализации.
Документ фиксирует решения из диалога. Ход реализации описан в
[плане небольших изменений](osinara-development-steps.md).

## 1. Выбранный подход и порядок работ

Выбран доменный модуль внутри существующего приложения Osinara.
Программный код рассчитывает и проверяет назначения, хранит версии и проверяет
полномочия. Агент принимает запросы, распознаёт данные, предлагает изменения
и объясняет сохранённые результаты.

1. Реализовать графики уборки и дежурств.
2. После них реализовать справочник жильцов.

Разработка ведётся через GitHub-форк исходного репозитория. Изменения делаются
небольшими последовательными шагами. Каждый шаг сопровождается подробным
объяснением для начинающего разработчика: задача, изменённый код, движение
данных, проверка и следующий шаг. Порядок описан в
[плане небольших изменений](osinara-development-steps.md).

На первом этапе предусмотреть постоянный внутренний идентификатор жильца.
На втором этапе расширить ту же запись контактами и другими данными.
Телефон, фотография и Telegram-привязка не обязательны для назначения дежурств.

## 2. Источник данных и ввод

- Google Sheets — основной источник актуальных данных о жильцах, сменах,
  исключениях и правилах.
- Владелец может вносить данные в таблицу или передавать агенту таблицу,
  фотографию таблицы и сообщения с исключениями.
- Агент показывает распознанные данные и предлагаемые изменения владельцу.
  Сохранение выполняется после его проверки и подтверждения.
- Подтверждённые изменения записываются в Google Sheets.
- База приложения хранит версии утверждённых графиков, историю и снимки
  использованных исходных данных и правил. Последующие изменения таблицы
  не переписывают исторические графики.
- Для разработки используются вымышленные жильцы и графики. Реальные данные
  и предыдущие дежурства загружаются позже через работающего агента.

Возможное разбиение таблицы для технического проектирования: жильцы, смены,
календарь, исключения и правила. Конкретные имена листов и столбцов не являются
продуктовым ограничением.

## 3. Объекты уборки

| Объект | Исполнителей | Периодичность | Время |
| --- | --- | --- | --- |
| Столовая | 2, вместе | Ежедневно | Утро или вечер по доступности пары |
| Первый этаж | 1 | Ежедневно | Утро |
| Второй этаж | 1 | Через день | Утро или вечер по доступности |
| Третий этаж | 1 | Через день | Утро или вечер по доступности |
| Прачка | 1 | Ежедневно | Вечер |
| Администрация | 1 | Ежедневно | Вечер |

Начальная настройка второго и третьего этажей — чередование. Дата начала
цикла задаётся при настройке. Сама одновременность уборки этих этажей для
владельца несущественна; параметры периодичности должны оставаться данными.
При начальном чередовании ежедневно требуется шесть разных исполнителей.

Для объектов без предпочтительного времени расчёт выбирает утро или вечер
и показывает выбранный период в черновике. Оба исполнителя столовой должны
быть доступны в один период. Точные часы пока не заданы.

## 4. Рабочие графики и доступность

Восемь человек работают по сменному графику, остальные — по 5/2. Общее число
жильцов определяется после загрузки данных.

| График / состояние дня | Утро | Вечер |
| --- | --- | --- |
| 5/2, рабочий день | Нет | Да |
| 5/2, свободный выходной | Да | Да |
| Сменный: дневная смена | Нет | Нет |
| Сменный: ночная смена | Да | Нет |
| Сменный: отсыпной | Нет | Да |
| Сменный: выходной в будний день | Нет | Да |
| Сменный: выходной в выходной день | Да | Да |

- Базовый календарь: понедельник–пятница рабочие, суббота–воскресенье выходные.
- Праздники и переносы владелец задаёт в общем календаре.
- Этот календарь также определяет тип дня для выходного сменного работника.
- Индивидуальные отклонения задаются исключениями только владельцем.
  При индивидуальной работе сотрудника 5/2 в выходной утром он недоступен.
- Для сменных работников загружается состояние каждого человека на каждую
  дату: дневная смена, ночная смена, отсыпной или выходной.
- Первая версия не продолжает сменный цикл автоматически за пределами данных.
- Неизвестный или противоречивый основной график исключает человека из
  автоматического назначения до уточнения. Владелец видит причину.
- Отсутствие исключения при известном основном графике означает обычный день
  по этому графику.

## 5. Распределение и равномерность

Жёсткие ограничения:

- Только доступные и не освобождённые на соответствующую дату люди.
- Максимум одно назначение на человека в день.
- Для столовой нужна совместно доступная пара.
- Все объекты равноценны. Каждому участнику пары засчитывается одно дежурство.

Сначала заполняется максимально возможное число мест с соблюдением ограничений.
Подбор выполняется совместно для всех объектов дня, чтобы заполнение одного
объекта не заблокировало допустимый полный вариант.

Порядок критериев выбора:

1. Меньшее число дежурств за последние 30 календарных дней перед датой графика.
2. При равенстве — человек, который дольше не дежурил.
3. Затем — человек, который дольше не убирал соответствующий объект.
4. При полном равенстве — устойчивый технический порядок для воспроизводимости.

Для графика на дату D окно статистики — D−30 … D−1 включительно. Например,
для 10 декабря учитываются назначения с 10 ноября по 9 декабря.

Нагрузка считается по действующим назначениям в утверждённых графиках и
загруженной истории. Черновики и отменённые назначения не учитываются.
Ежедневное подтверждение фактической уборки не требуется.

Если прошлые дежурства не загружены, агент просит историю либо явное решение
владельца «начать учёт с нуля». При таком решении всем задаётся одинаковая
начальная нагрузка, а в объяснениях указывается дата начала учёта.

При нехватке людей:

- Ограничения доступности и одного назначения в день сохраняются.
- Незакрытые места явно показываются владельцу.
- Столовая считается закрытой только при наличии пары. Один исполнитель может
  быть показан отдельно как неполный вариант, без статуса готового назначения.
- Владелец может утвердить неполный график. Пропуски видны в черновике,
  подтверждении и опубликованном сообщении.

## 6. Черновик, утверждение и публикация

1. Владелец в личном чате запрашивает график на указанную дату.
2. Приложение загружает и проверяет данные, рассчитывает назначения и сохраняет
   версию черновика вместе с основаниями выбора.
3. В личном чате владелец видит объекты, время, исполнителей, объяснения,
   незакрытые места и выявленные проблемы данных.
4. Владелец может запросить исправление; оно создаёт новую версию черновика.
5. Публикация выполняется после подтверждения владельца в личном чате.
   Подтверждение относится к конкретной версии и конкретной группе.
6. В группу отправляется сохранённая утверждённая версия. Агент не пересчитывает
   назначения в момент отправки.

На одну дату действует одна утверждённая версия графика. После подтверждения
исправления она заменяет предыдущие назначения в статистике. Старые версии
и факты публикации сохраняются. Для уже опубликованного графика в группу
отправляется явное исправление с указанием действующей версии.

Жильцы задают вопросы об опубликованных назначениях в общем чате. Ответы
опираются на сохранённый график и основания расчёта.

## 7. Изменение правил

- Все поддерживаемые параметры представлены редактируемыми данными.
- Владелец меняет правила через личный диалог.
- Агент показывает конкретные изменения для проверки перед сохранением.
- Изменения применяются к новым графикам.
- Опубликованные версии сохраняются с использованной версией правил.
- Новый принципиальный тип ограничения может потребовать расширения программы.

## 8. Справочник жильцов — второй этап

Справочник расширяет тот же список жильцов в Google Sheets. Общий постоянный
ID связывает контакты, рабочий график и историю назначений.

Карточка может содержать:

- Имя и фамилию.
- Фотографию.
- Номер телефона.
- Подтверждённую связь с Telegram-аккаунтом.
- Дополнительные поля по мере необходимости.

Сценарии поиска:

- По имени и/или фамилии: «Как написать Ивану Петрову?».
- По автору сообщения, на которое пользователь отвечает: «Кто это?».
- При нескольких совпадениях агент показывает варианты и уточняет человека
  перед выдачей полной карточки. При совпадении полных имён можно использовать
  фотографии карточек.

Создавать и изменять карточки может только владелец.

Telegram-привязка:

- Используется проверенный числовой Telegram ID; username не является ключом.
- Совпадение имени или ника помогает предложить кандидата.
- Привязку подтверждает владелец на основании проверенного ID из сообщения.
- При отсутствии привязки агент сообщает об этом.
- Наличие username и его неизменность не предполагаются. Способ показа
  доступного контакта без username проверяется при реализации.

Фотография:

- Владелец загружает фото или выбирает доступный аватар Telegram.
- Сохранённое фото меняется только по указанию владельца.
- При отсутствии фото выдаются остальные известные поля.

Доступ:

- Участникам указанной внешней группы доступны имя, фамилия, Telegram-контакт,
  телефон и фотография найденного жильца.
- Дополнительные поля доступны только владельцу в личном чате.
- Выдача справочника в других чатах в первую версию не входит.

Выезд:

- Владелец задаёт дату выезда.
- С этой даты человек исключается из новых назначений и обычного поиска.
- История сохраняется; архивная карточка доступна владельцу.
- Выход из Telegram-группы сам по себе не изменяет статус проживания.

## 9. Необходимые изменения проекта

План первого этапа:

1. Добавить модуль `agent/lib/duty-scheduling/`, модель жильцов, схемы данных,
   версии правил, импорт и миграции PostgreSQL.
2. Настроить существующее подключение Google Sheets: чтение, предпросмотр
   изменений и запись после подтверждения владельца. Добавить предметную
   проверку, обнаружение конфликтов с изменёнными строками и снимки данных
   расчёта. Общий доступ к Google-инструментам во внешнюю группу не выдавать;
   инструменты группы читают разрешённые результаты доменного модуля.
3. Реализовать расчёт всех назначений дня, проверки ограничений и сохраняемые
   основания выбора на вымышленных данных.
4. Добавить инструменты подготовки и просмотра черновика, изменения правил,
   утверждения/публикации и чтения опубликованных назначений.
5. Подключить существующие проверки владельца и подтверждения действий.
   Для внешней группы предоставить ограниченные инструменты чтения.
6. Реализовать журнал доставки и обработку повторных нажатий, сбоев и
   неопределённого результата отправки без слепой повторной публикации.
7. Проверить сценарии и собрать отдельный образ приложения; учесть существующий
   механизм обновления Osinara при выборе способа выпуска изменений.

План второго этапа:

1. Расширить общую запись жильца полями справочника.
2. Добавить инструменты владельца для импорта, изменения и Telegram-привязки.
3. Добавить поиск по имени и проверенному автору сообщения с уточнением совпадений.
4. Подключить выдачу разрешённых полей, фотографии и доступного Telegram-контакта.
5. Проверить архивирование, права доступа и отсутствие обязательной зависимости
   от username.

## 10. Критерии приёмки

Первый этап:

- Все строки матрицы доступности воспроизводятся на тестовых данных.
- Нет двух назначений одному человеку в день.
- Столовая получает двух совместно доступных исполнителей либо отмечается
  незакрытой; график не выдаёт неполную пару за готовое назначение.
- Работают чередование этажей, календарь и исключения владельца.
- Выбор учитывает окно D−30 … D−1 и согласованный порядок критериев.
- Черновики не изменяют нагрузку, замена утверждённой версии не удваивает её.
- Без подтверждения владельца конкретная версия не публикуется.
- Смена текста, назначений или адресата не использует старое подтверждение.
- Незакрытые места сохраняются во всех представлениях неполного графика.
- Ответы жильцам соответствуют действующей опубликованной версии.
- Ошибки распознавания и неизвестная доступность видны владельцу.
- Поддерживаемые изменения правил не требуют правки исходников.

Второй этап:

- Один человек связан с одной общей записью независимо от смены фамилии/ника.
- Поиск работает по имени, фамилии и проверенному автору сообщения.
- Неоднозначность вызывает уточнение, отсутствие поля не приводит к выдумыванию.
- Только владелец создаёт/изменяет карточки и подтверждает Telegram-привязку.
- Группа получает только согласованные поля; архив и дополнительные поля
  остаются доступны владельцу.
- Фото и Telegram username могут отсутствовать.

## 11. Параметры, которые задаются позже

Через настройку и загрузку данных в работающем агенте нужно указать:

- Google-аккаунт, таблицу и соответствие полей.
- Внешнюю Telegram-группу для публикаций и справочника.
- Часовой пояс дома.
- Дату начала чередования второго и третьего этажей.
- Жильцов и сроки проживания, календарь смен, исключения и прошлые дежурства
  либо решение начать учёт с нуля.
- Фотографии, телефоны и подтверждённые Telegram-привязки для второго этапа.

Эти реальные данные не нужны для разработки: вместо них используются
вымышленные примеры. Точные часы периодов «утро» и «вечер» пока не заданы;
начальная модель доступности оперирует самими периодами.

## 12. Проверенная исходная установка

На момент исследования 7 ноября 2026 года установлен Osinara v1.8.56,
commit f4c4e1b, Docker,
каталог `/opt/osinara`. Зарегистрированных групп нет, Google Workspace
отключён. Программный код встроен в образ приложения.

В проекте уже есть Telegram, PostgreSQL, owner-only проверки, подтверждения
действий, создаваемые навыки и проверенная идентификация автора reply.
Один создаваемый навык не добавляет серверные инструменты и не обеспечивает
публикацию утверждённой версии графика в другом чате.

Google-интеграция уже поддерживает чтение и запись Sheets, OAuth scope для
таблиц и подтверждение операций записи. Новые общие маршруты Sheets не нужны;
необходимы настройки подключения и предметные инструменты владельца.
Приём фотографий в личке и анализ изображений также уже поддерживаются.

Опорные места исходного кода установленной версии:

- [Чтение и запись Google Workspace](https://github.com/ilkruglov/osinara/blob/f4c4e1b/agent/lib/google-workspace/google-workspace-command-policy.ts).
- [Подтверждение Google-операций](https://github.com/ilkruglov/osinara/blob/f4c4e1b/agent/lib/tools/execute_google_workspace.ts).
- [Проверка подтверждения конкретного вызова](https://github.com/ilkruglov/osinara/blob/f4c4e1b/agent/lib/telegram-hitl/approval-evidence.ts).
- [Проверенная идентификация автора reply](https://github.com/ilkruglov/osinara/blob/f4c4e1b/agent/lib/telegram-profile-subjects.ts).

Продуктовые решения этого документа не означают, что изменения уже внесены
в исходники или работающий экземпляр.
