# Шаг 8.1. Подготовка и просмотр графика в диалоге владельца

## Задача и результат

В предыдущих шагах появились расчёт, хранение версий и чтение таблицы.
Теперь добавлен инструмент `manage_duty_schedule`, который связывает их
с основным агентом в личном диалоге владельца. После установки этой версии
агент сможет найти внешнюю группу, подготовить черновик на точную дату
из её сохранённого источника и показать назначения с основаниями выбора.

Это изменение в форке. Работающая установка пока не обновлена.
Инструмент настройки источника появится в шаге 8.2: сейчас сохранённая
конфигурация уже должна существовать. Для разработки она создаётся
на вымышленных данных в отдельной тестовой базе.

## Пример диалога

Владелец: «Подготовь график уборки на 9 ноября 2026 года».

Агент вызывает `groups`, получает зарегистрированные группы и наличие
источника. Если подходящих групп несколько, уточняет выбор. После этого
вызывает `prepare` с выбранным ID и датой `2026-11-09`.

В результате — ID и номер сохранённой версии, черновик с именами,
утренними/вечерними периодами, нагрузкой и датами прошлых дежурств.
Для столовой видно, что два исполнителя назначены вместе. При нехватке
людей видны незакрытые места; неизвестные смены не считаются выходными.

Агент показывает владельцу этот результат. Утверждение и публикация
этим инструментом не выполняются. Значение `canApprove` означает лишь,
что полнота графика удовлетворяет правилам; согласие владельца оно не заменяет.

«Сервис» здесь означает функцию, которая организует несколько действий.
«Репозиторий» — модуль чтения и записи базы, а не GitHub-репозиторий.
«Снимок» — сохранённые исходные данные, правила, история и результат расчёта.
При просмотре снимка назначения не рассчитываются заново.

```text
личный запрос владельца
  manage_duty_schedule
    проверка действия, личного контекста и роли в базе
    groups → внешние группы своей семьи
    prepare → сохранённый источник → проверенное чтение таблицы
            → расчёт и сохранение версии → представление владельцу
    get/latest → сохранённая версия → то же представление
```

## Четыре действия

В примерах ниже значения `<groupId>` и `<id>` нужно заменить настоящими UUID
из результата инструмента. Их не следует придумывать.

```json
{ "action": "groups" }
{ "action": "prepare", "groupId": "<groupId>", "date": "2026-11-09" }
{ "action": "get", "id": "<id>" }
{ "action": "latest", "groupId": "<groupId>", "date": "2026-11-09" }
```

`groups` возвращает группы и версию настройки источника, но не Google-профили
или содержимое таблицы. `prepare` читает источник, рассчитывает и сохраняет
новый черновик. `get` читает конкретную версию. `latest` находит последнюю
сохранённую версию на дату, включая её текущий статус: она не обязательно
утверждена. Для `latest` группа должна оставаться зарегистрированной;
старую версию по известному ID владелец может прочитать из архива и после
удаления регистрации группы.

Внешняя схема инструмента — обычный объект, как требует Eve. Внутри программы
для каждого действия проверяется точный набор полей. Например, `prepare`
без даты или `groups` с лишним полем отвергается с понятной ошибкой.
В параметры нельзя передать жильцов, историю, источник или ID владельца:
сервер сам выбирает данные и проверяет пользователя.

## Почему повтор не должен менять черновик

Для `prepare` сервер строит ключ из ID сессии и ID вызова инструмента.
Перед чтением Google проверяет, сохранялся ли результат этого вызова.
Если да, возвращает прежний снимок с `reused: true`, даже если таблица
уже изменилась или Google недоступен. Попытка использовать тот же вызов
для другой группы или даты заканчивается конфликтом.

Новый вызов — новый запрос на расчёт и новая версия. После ошибки с неясным
результатом записи агенту предписано сначала вызвать `latest` и проверить
сохранённое состояние. Автоматически запускать новый `prepare` не следует.
Защита повтора использует ID вызова, а не просто совпадение текста просьбы.

## Что сохраняется и проверяется

Снимок дополнен названием группы и происхождением данных: ID и номером
конфигурации источника, хешем прочитанного содержимого. Хеш — вычисленная
контрольная сумма: она помогает связать результат с конкретным чтением.
Старые снимки остаются читаемыми без этих дополнительных полей; при
отсутствии названия показывается сохранённый Telegram ID группы.
Изменять схему SQL или переписывать старые версии не требуется.

Источник проверяется после Google-запроса и ещё раз внутри транзакции
сохранения. Транзакция — блок операций базы, который фиксируется целиком.
При сохранении используется та же блокировка, что при смене источника:
новая конфигурация не сможет незаметно подменить происхождение черновика.
Если версия уже другая, нужно заново прочитать источник и подготовить график.

Инструмент доступен основному агенту в личном режиме. Проверка обработчика
дополнительно запрещает фоновые и дочерние вызовы. Реальная роль владельца
повторно проверяется в PostgreSQL: одного текста `role=owner` недостаточно.
Чужие группы и версии недоступны. Создание обратимого черновика не требует
процедуры подтверждения публикации.

Представление строится только из снимка: имена, назначения, периоды,
нагрузка, даты прошлых дежурств, правила сравнения и незакрытые места.
Полная исходная таблица, контакты и сырая история в ответ не включаются.
Имена и названия считаются данными, управляющие символы убираются, слишком
длинные значения сокращаются; одинаковые имена дополняются ID жильца.

Сначала расчёт закрывает максимум мест, затем сравнивает нагрузку и
остальные критерии по сохранённому приоритету. Поэтому показанная нагрузка
объясняет выбор в контексте всего графика, а не обещает, что каждый объект
получит первого кандидата из отдельного списка.

## Текущие границы

Поддерживаются точные даты `YYYY-MM-DD`. Неоднозначные и относительные даты
агент должен уточнять, вместе с группой при нескольких вариантах.
Отсутствие источника, истории или смен не заменяется выдуманными данными.
Начать учёт с нуля можно только явной настройкой данных.

Один просмотр ограничен 150 местами, 50 объектами, 150 жильцами с неизвестными
сменами и 128 КиБ ответа. При превышении возвращается ошибка с требованием
постраничного просмотра; такой просмотр пока не реализован. Проверка размера
представления выполняется после сохранения: слишком большой черновик может
остаться в базе. Для текущих шести мест на дату ограничение не мешает.
Назначения не обрезаются молча.

Настройка источника через диалог, правки таблицы и правил, утверждение,
публикация и ответы жильцам добавляются следующими изменениями.

## Почему примеры переехали

Eve рассматривает файлы внутри `agent/lib` как модули программы. Проверка
основной сборки обнаружила, что три старых JSON-примера в `fixtures`
не подходят этому формату. Они перенесены без изменения содержимого в
`examples/duty-scheduling`. Пути в скриптах, тестах и учебных документах
обновлены. Теперь исходные данные отделены от исполняемых модулей,
а основная сборка проходит.

## Учебный запуск

Скрипт требует отдельную PostgreSQL-базу с суффиксом `_test` и миграциями
001–148. Реальные Google и Telegram не вызываются: таблица берётся из
`examples/duty-scheduling/sheets-example.json`, пользователь и семья вымышлены.
Проверка роли в базе при этом настоящая.

Для создания отдельной базы можно использовать рецепт контейнера из
[шага 7.3](duty-sheets-step-7-3.md#учебный-запуск), затем из корня проекта:

```sh
DATABASE_URL="$DUTY_DEMO_DATABASE_URL" node --import tsx scripts/demo-duty-owner-dialog.ts
```

`DUTY_DEMO_DATABASE_URL` должен указывать именно на учебную базу. Не подставляйте
адрес работающего агента. Скрипт создаёт свою тестовую семью, читает группы,
сохраняет черновик, переподключается к базе и читает ту же версию. В конце
удаляет только свои тестовые записи. Ожидаемые последние строки:

```text
После переподключения та же версия: true
Повтор использовал снимок: true; чтений Google-модели: 1
Утверждение и публикация не выполнялись. Реальных Google/Telegram-запросов нет.
```

## Проверки

На отдельном временном PostgreSQL, под ограниченной ролью `osinara_app`,
проверяются настоящий SQL и права, а Google заменён тестовым транспортом.
Общий выбранный набор — 356 тестов: 301 тест дежурств и 55 тестов каталога
и доступности инструментов. В новых проверках есть повтор вызова, смена
источника перед сохранением, отключённый Google, отозванная роль владельца,
чужая семья, архив группы, фоновые и дочерние вызовы.

```sh
RUN_DATABASE_INTEGRATION_TESTS=true DATABASE_URL="$DUTY_TEST_DATABASE_URL" \
  node_modules/.bin/vitest run agent/lib/duty-scheduling \
  agent/lib/tool-policy/mode-tool-surface.trusted.test.ts \
  agent/lib/tool-policy/mode-tool-surface.test.ts \
  agent/lib/tool-policy/dynamic-capabilities.test.ts \
  agent/lib/tool-surface.test.ts --maxWorkers=1
npm run typecheck
node_modules/.bin/eve build --skip-sandbox-prewarm
node --experimental-strip-types scripts/validate-eve-tool-surface-build.ts
```

Этот набор, общая проверка типов, сборка основного агента и проверка его
скомпилированного каталога инструментов прошли. Сборка выполнена без
подготовки sandbox; это не полная агрегированная сборка всех приложений.
Учебный скрипт также прошёл. Реальный личный диалог, живая Google-таблица
и отправка Telegram здесь не проверялись; они потребуют отдельной приёмки
при подготовке выпуска.

и сохранить её после точного подтверждения в личном диалоге.
