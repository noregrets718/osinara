# Шаг 4. История нагрузки и порядок кандидатов

## Результат

Функция `rankDutyCandidates` получает проверенные данные дома, историю,
ID объекта и дату графика. Возвращает доступных кандидатов в порядке выбора,
а также показатели, объясняющие этот порядок.

В вымышленном примере на 9 ноября для первого этажа доступны утром:

| Кандидат | Нагрузка | Последнее дежурство | Порядок |
| --- | --- | --- | --- |
| Николай Сценариев | 1 | 6 ноября | Первый |
| Пётр Тестов | 2 | 6 ноября | Второй |

Давность одинакова, но у Николая меньше нагрузка. Поэтому следующий критерий
здесь уже не нужен.

## Файлы и движение данных

```text
example.json → parseDutyData ───────┐
                                  ├→ rankDutyCandidates → список и показатели
history.json → parseDutyHistory ───┘
```

| Файл | Назначение |
| --- | --- |
| `duty-history.ts` | Формат истории, ссылки на жильцов/объекты, проверка версий |
| `duty-candidates.ts` | Окно нагрузки, доступность и сравнение кандидатов |
| `fixtures/history.json` | Вымышленные утверждённые, заменённые, отменённые и черновые версии |
| `duty-history.test.ts`, `duty-candidates.test.ts` | Проверки целостности истории и справедливости порядка |
| `scripts/show-duty-candidates.ts` | Таблица кандидатов в терминале |

Пути первых пяти файлов начинаются с `agent/lib/duty-scheduling/`.
История хранится отдельным входным снимком: формат данных шагов 1–3
и существующие примеры продолжают работать.

## Откуда начинается учёт

У истории есть три режима:

- `not_loaded` — история ещё не загружена. Расчёт просит загрузить её либо
  явно выбрать начало с нуля.
- `imported` — история полна начиная с `fromDate`. Она должна покрывать всё
  запрошенное окно; более поздняя дата начала вызывает ошибку, а не нулевую нагрузку.
- `zero_start` — отражает явное решение начать учёт с `fromDate`. До неё
  дежурства не предполагаются известными, и дата начала возвращается в результате.

Например, подтверждённое начало с нуля:

```json
{ "mode": "zero_start", "fromDate": "2026-11-09", "schedules": [] }
```

Это формат данных, а не проверка полномочий. В рабочем агенте такое решение
будет приниматься через инструменты владельца в следующих шагах.
Записи раньше `fromDate` отклоняются: нужно уточнить период учёта или саму историю.

## Версии графиков

Каждая запись содержит `id`, `date`, `version`, `status` и назначения.
Статусы: `draft` — черновик, `approved` — действующая утверждённая версия,
`cancelled` — отменённая, `superseded` — заменённая новой версией.

Нагрузка учитывает только `approved`. Старую версию на ту же дату нужно
пометить `superseded`. Две действующие утверждённые версии вызывают ошибку:
программа не выбирает одну наугад и не удваивает нагрузку.

Назначение хранит `residentId`, `objectId` и исторический зачёт `credit`.
В столовой два назначения разным людям дают по одной единице каждому.
Повтор одного человека на одном объекте в одной версии отклоняется.
Сегодняшние ограничения не проверяются задним числом: прежние версии правил
могли допускать несколько назначений в день или другой состав группы.

## Что попадает в 30 дней

Для даты D используются назначения с D−30 по D−1 включительно.
Например, для 10 декабря — с 10 ноября по 9 декабря. На саму дату графика
и после неё назначения не учитываются: это позволяет пересчитать замену
графика без влияния его прежних назначений на нагрузку.

Длина окна берётся из `rules.lookbackDays`. Разница считается календарными
днями в UTC, включая границы года и 29 февраля.

У кандидата есть:

- `dutyCount` — количество назначений в окне;
- `load` — сумма их сохранённого зачёта;
- `lastDutyDate` — последнее действующее назначение до D во всей загруженной истории;
- `lastObjectDate` — последнее такое назначение на выбранном объекте.

При начальных правилах зачёт каждого назначения равен `1`, поэтому нагрузка
совпадает с количеством дежурств. Если поддерживаемый зачёт изменится,
прошлые записи сохранят прежние значения. Критерий `least_duties` сравнивает
нагрузку в единицах зачёта. Изменение сегодняшнего `creditPerPerson` не
пересчитывает исторический `credit`.

`null` в дате означает «не найдено в загруженной истории», а не «никогда
в жизни не дежурил». Если с начала полного учёта назначений не было,
такой кандидат дежурил раньше любого кандидата с известной датой либо ещё
не дежурил — поэтому при равной нагрузке он идёт раньше.

## Как сравниваются кандидаты

Сначала функция из шага 2 определяет доступные периоды. Если ни один из них
не подходит объекту, человек не попадает в список. Остальные сравниваются
последовательно по `rules.priorities`:

1. Меньше нагрузка.
2. При равенстве — более раннее последнее дежурство.
3. Затем — более ранняя последняя уборка этого объекта.
4. При полном равенстве — постоянный ID для воспроизводимости.

Список критериев и его порядок — редактируемые данные. Исходные массивы,
правила и история не изменяются: сортируется новый массив результатов.

Ранжирование показывает кандидатов для указанного объекта. Выбор нужных
объектов на дату остаётся функцией шага 3. Следующий шаг соединит эти данные
в общий график, учитывая совместную пару и предел назначений на человека.

## Проверка в VS Code

Из корня проекта:

```sh
node --import tsx scripts/show-duty-candidates.ts 2026-11-09 floor-1
node --import tsx scripts/show-duty-candidates.ts 2026-11-09 dining
```

В таблице видны периоды, количество дежурств, нагрузка и последние даты.
После даты и ID объекта можно передать путь к своим данным и путь к истории.
Все данные примеров вымышленные; реальные сведения пока не загружаются.

Тесты модуля:

```sh
npm test -- agent/lib/duty-scheduling --maxWorkers=1
```

Проверяются границы окна, замена версий, зачёт пары, порядок критериев,
давность за пределами окна, доступность, явное начало с нуля, нехватка
истории, сохранение старого зачёта и неизменность исходных данных.
