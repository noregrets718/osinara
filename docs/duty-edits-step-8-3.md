# Шаг 8.3. Правки данных и правил через личный диалог

## Задача и результат

Владелец сможет попросить изменить рабочую смену, исключение доступности,
параметры объекта или поддерживаемое правило. Агент прочитает данные из
сохранённого источника группы, подготовит конкретные изменения и запросит
подтверждение. После согласия выполнится одна попытка записи с проверкой.

Добавлены два инструмента:

- `inspect_duty_sheet_changes`: читать поддерживаемые строки, готовить
  неизменяемый предпросмотр, проверять статус попытки;
- `apply_duty_sheet_changes`: записать конкретный сохранённый предпросмотр
  после точного подтверждения владельца.

Это код в форке; установленный агент пока не обновлён. В разработке
используется отдельная тестовая база и модель Google, реальные данные не меняются.

## Пример для изучения

Владелец: «Теперь сравнивай нагрузку за последние 14 дней».

Агент читает строку `lookbackDays` раздела `settings`, видит прежнее значение
`30`, затем готовит правку:

```json
{
  "action": "preview",
  "groupId": "<ID группы из manage_duty_schedule groups>",
  "edits": [
    { "action": "upsert", "section": "settings", "key": "lookbackDays", "values": { "value": 14 } }
  ]
}
```

Предпросмотр покажет изменение `30 → 14` и автоматическую смену `rulesVersion`.
Он получает свой ID. Для подтверждения агент передаёт только:

```json
{ "previewId": "<ID сохранённого предпросмотра>" }
```

Окно Telegram покажет группу, таблицу, личный профиль и все изменяемые ячейки:
какой лист, строка и поле, прежнее и новое значение. Кнопка — «Записать правки».
После нажатия таблица читается ещё раз. Если она соответствует просмотренной
версии, правки отправляются и результат проверяется повторным чтением.

## Чтение и постоянные ключи

В `read` передаются группа и раздел, необязательно конкретный ключ или `offset`:

```json
{ "action": "read", "groupId": "<UUID группы>", "section": "settings", "key": "lookbackDays" }
```

Сервер возвращает только столбцы, поддерживаемые модулем дежурств, с именами
полей для `values`. Дополнительные телефон, фотография и другие столбцы
справочника в ответ не попадают. Полная история назначений также не возвращается.
Страница содержит максимум 50 строк; `total` и `nextOffset` показывают,
сколько есть данных и как получить следующую страницу. Пустой результат
не означает разрешение придумать отсутствующие данные.

| Раздел | Постоянный ключ | Пример изменяемых полей |
| --- | --- | --- |
| `residents` | `id` жильца | `firstName`, `lastName`, `workSchedule`, `inactiveFrom` |
| `objects` | `id` объекта | `people`, `samePeriod`, `periods`, `everyDays`, `anchorDate` |
| `workShifts` | `residentId/YYYY-MM-DD` | `residentId`, `date`, `state` |
| `calendarOverrides` | `YYYY-MM-DD` | `date`, `isDayOff` |
| `exceptions` | `residentId/YYYY-MM-DD` | `residentId`, `date`, `morning`, `evening` |
| `settings` | имя настройки | `value` |
| `availability` | тип дня | `morning`, `evening` |

Для `state` используются `day`, `night`, `recovery`, `off`. Даты — точные
календарные `YYYY-MM-DD`. ID жильца переживает изменение фамилии. При нескольких
совпадениях имени агент должен уточнить выбор, а не назначить произвольный ID.

`upsert` меняет только переданные поля существующей строки. Для новой строки
нужно передать все обязательные данные, включая поля её постоянного ключа.
Изменить ключ существующей строки нельзя. `remove` разрешён только для смен,
календарных исключений и исключений доступности: очищаются поддерживаемые
ячейки строки, а не удаляется строка листа. Для выезда жильца меняется
`inactiveFrom`; его ID и история сохраняются.

За один запрос поддерживается 1–10 различных строк. Неизвестные поля,
настройки, невалидные даты, ссылки на несуществующих жильцов и некорректные
сочетания правил отклоняются до записи. Принципиально новый тип правила
по-прежнему требует изменения программы.

## Почему сохраняется предпросмотр

Подтверждаемое действие получает только ID, а не источник, значения или
адреса ячеек от модели. По этому ID сервер загружает неизменяемые входные
данные и план. PostgreSQL запрещает менять или отдельно удалять запись
предпросмотра. Контрольная сумма дополнительно связывает входные данные
и план; они проверяются при чтении.

Подтверждение относится к этому ID, конкретному вызову инструмента,
действующей личной сессии и Telegram-владельцу. Оно не подходит к другому
предпросмотру или действию. Роль повторно проверяется в базе. Обработчик
также запрещает групповые, фоновые и дочерние вызовы.

Перед отправкой программа сверяет и сам план: адреса ячеек, значения
«было/стало» и ожидаемые данные должны соответствовать сохранённому просмотру.
Поэтому обновление кода или внутренняя ошибка не должны незаметно заменить
состав подтверждённой записи. Предпросмотр не содержит всей исходной таблицы
или дополнительных контактов — только поддерживаемые правки и их основания.

Для правил используется прежний механизм шага 7.2: изменение содержимого
правил, объектов или часового пояса автоматически создаёт новый номер правил,
если владелец не передал его явно. Эта дополнительная ячейка тоже входит
в просмотр и подтверждение. Сохранённые графики сохраняют прежние снимки;
новый расчёт прочитает актуальные данные и правила.

## Проверка источника и ограничения Google

Предпросмотр связан с группой, ID и номером сохранённой конфигурации источника.
Источник выбирает сервер. При его смене во время просмотра предпросмотр
не сохраняется. Конфигурация проверяется в транзакциях начала попытки
и перехода в `writing`, под той же блокировкой, что её изменение.

После перехода в `writing` операция уже относится к зафиксированному
подтверждённому источнику. Более поздняя смена настройки группы не перенаправляет
начатую запись в другую таблицу и не отменяет уже отправленный запрос Google.

Перед записью таблица читается в режиме формул. Редактирование поддерживается
для данных без формул; формулы не превращаются незаметно в вычисленные значения.
Изменение любого прочитанного содержимого после просмотра вызывает конфликт.
Отправка использует `RAW`: строки не интерпретируются как формулы.

Ограничение Google из шага 7.2 сохраняется: между последним чтением и отправкой
человек всё ещё может вручную изменить таблицу. Эти вызовы не создают
транзакцию Google и не блокируют ручные правки. Для совместной работы нужен
согласованный порядок изменения таблицы.

Снимок предпросмотра ограничен 64 КиБ, страница чтения — 128 КиБ ответа.
Также действует прежний предел команды Google в 3000 символов JSON.
Слишком крупный пакет отклоняется целиком; подтверждённые правки не разбиваются
на скрытые отдельные отправки и значения не обрезаются молча.

## Статус и неясный исход

```json
{ "action": "status", "operationId": "<ID из предпросмотра или результата>" }
```

| Статус | Как объяснить владельцу |
| --- | --- |
| `checking` | Проверка ещё не завершена; повторная отправка запрещена |
| `writing` | Запись начата, исход пока не известен |
| `applied` | Запись выполнена и проверена; только здесь `completed=true` |
| `conflict` | Таблица изменилась; правки не отправлены, нужен новый просмотр |
| `failed` | Попытка остановлена до отправки; сначала исправить причину |
| `unknown` | Правки могли примениться; повтор и новые записи заблокированы до сверки |
| `reviewed` | Спорная попытка закрыта решением владельца; это не доказанный успех |

Повтор того же `previewId` возвращает прежнюю попытку без повторной отправки.
После ошибки сначала читается статус. Новый ID не является способом обойти
блокировку `checking`, `writing` или `unknown`. Успешная запись данных
не утверждает график и не публикует его в группу.

Механизм сверки спорных записей уже реализован в шаге 7.3; интерфейс владельца
для него добавляется следующим небольшим шагом 8.4. Пока этот выпуск не
установлен на работающего агента, незавершённый интерфейс восстановления
не затрагивает реальные операции.

## Учебный запуск и проверки

Нужна отдельная база с суффиксом `_test` и миграциями 001–149. Пример создания
контейнера есть в [шаге 7.3](duty-sheets-step-7-3.md#учебный-запуск).
После миграций из корня проекта:

```sh
DATABASE_URL="$DUTY_DEMO_DATABASE_URL" node --import tsx scripts/demo-duty-edit-dialog.ts
```

Скрипт создаёт вымышленные семью, владельца и источник, показывает изменение
`lookbackDays`, текст подтверждения, имитирует точную запись о согласии в
тестовой базе и вызывает настоящий механизм журнала. Google заменён моделью
таблицы в памяти. После переподключения повторяется тот же ID:

```text
Результат: applied; completed=true. Отправок модели Google: 1.
Повтор после переподключения: applied. Отправок по-прежнему: 1.
```

В конце удаляются только созданные скриптом тестовые записи.
Прогон выполнен под ограниченной ролью `osinara_app`, как и интеграционные
тесты. Реальные Google и Telegram не вызывались.

Прошли 439 тестов в 27 файлах: дежурства, доступность инструментов,
представление, доставка и группировка подтверждений. В новых сценариях есть
пагинация, неизменность предпросмотра, подмена входных данных и плана,
старый снимок правил, смена источника, ручная правка, чужой предпросмотр,
отозванная роль, повтор и блокировка после неопределённого исхода.

Также прошли проверка типов всего проекта, целевой `oxlint`, сборка основного
агента `eve build --skip-sandbox-prewarm` и проверка собранного каталога
`scripts/validate-eve-tool-surface-build.ts`. Подготовка sandbox и полная
агрегированная сборка приложений не входили в этот прогон.
Живая Google-таблица и реальный личный диалог потребуют приёмки перед выпуском.
